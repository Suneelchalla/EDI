What EDI is, in one minute

UN/EDIFACT

EDI is how trading partners exchange business documents as structured data instead of paper or email. Liner shipping mostly uses UN/EDIFACT — a UN standard that nests data like envelopes inside envelopes:

UNB·UNZ
Interchange
UNG·UNE
Group (opt)
UNH·UNT
Message
seg
Segment
elem
Element

One interchange carries one or more messages; each message is a stack of segments (BGM, DTM, LOC…); each segment holds data elements. A segment is Mandatory or Conditional and can repeat. That's the whole idea.

Not only EDIFACT. Your platform also speaks ANSI X12 with some partners — e.g. GRIFFIN uses X12 322 (terminal operations). X12 is the North-American EDI standard; same idea (envelopes → segments → elements), different syntax and code sets.

The codes behind your mappings

ISO · UN/LOCODE

ISO 6346 — containers

The global standard for identifying containers (owner code + serial + check digit) plus a 4-character size/type code. Examples: 22G1 20ft standard, 42G1 40ft standard, 45G1 40ft high-cube. This is what ISO / Equipment mapping translates.

UN/LOCODE — ports & places

The UN code for ports, terminals and logistics locations (e.g. INMAA Chennai, SGSIN Singapore). Bills of lading and customs filings ride on these — and Port Code Mapping bridges your line port code to the customs authority's expected code.

The rules that drive the messages:

SOLAS VGM. IMO, SOLAS Ch VI Reg 2 — in force 1 July 2016. The shipper named on the BL must declare a verified container weight before loading; filed via VERMAS or a carrier portal. No VGM = the box isn't loaded.
Advance manifests. US AMS / ACE — the 24-hour advance cargo rule to CBP, filed as EDIFACT CUSCAR or ANSI 309. EU ICS2 / ENS — Entry Summary Declaration with advance cargo data before arrival.
Where it's heading. Alongside classic EDI, the industry is standardizing on DCSA APIs and the electronic bill of lading (eBL) — so expect JSON/REST to sit next to EDIFACT/X12 over time.

Step 1 · Classify the failure

New_knowledge_base

Before changing any mapping, decide which kind of failure it is. Pick one:

Documented Fix in EMS EDI Configuration

COARRI processing depends on the required movement codes being mapped per Partner/EDI. If a code isn't mapped, or the incoming segment differs from the mapped one (e.g. SNTS), the file lands in EMS Gate error.

  1. Get the actual EDI file — partner-specific mapping means you can't diagnose without it.
  2. Identify the BGM and the actual segment present in the file.
  3. Compare against EMS EDI Configuration for that Partner/EDI.
  4. Add the missing movement-code / segment mapping.
  5. Reprocess. A mapping request should always carry the file + exact BGM/segment.

Documented Fix the owning module, then let the back job run

The record sits as Not Approved in EMS Gate. When the upstream condition is corrected and the back job runs, EMS Auto Reprocess re-validates and approves it — you usually don't touch the EDI at all. Which module? See the error-code table below (BC, PA, IW, ITT).

  1. Read the EMS Gate error code to find the owning module.
  2. Correct the state there (backdate Booking, approve Work Order, supply Vessel/Voyage…).
  3. Wait for the back job — Auto Reprocess approves the Gate record automatically.

Documented Action Not Required — review, don't panic

A duplicate is not a system error. The record stays visible in EMS Gate for reference and is cleared manually — it does not vanish on its own.

Exact duplicateContainer No + Movement Code + exact Activity Date/Time all match.
Logical duplicateContainer No + Movement Code + Terminal/Depot + Booking No match, and Activity Date/Time within ±5 days.

Step 1 · Classify the failure

New_knowledge_base

The three IGM failures look alike but branch completely differently:

Documented Import Documentation isn't saved

A BL only loads into IGM EDI Generation once its Import Documentation is saved. This is a different branch from "present but blocked" — don't jump to mappings yet.

  1. Confirm the BL exists and belongs to the selected Voyage/Port.
  2. Open Import Documentation for that BL/shipment.
  3. Complete and Save it.
  4. Return to IGM EDI Generation → Show; the BL now loads.

Documented Required mapping is missing

Message: Mapping yet to be created. Hence IGM cannot be generated for below BLs. Usually the mandatory Line Port Code ↔ Customs Port Code mapping. The BL can be perfectly valid — this is the translation layer, not the business data.

  1. Note the port(s) on the blocked BL(s).
  2. Verify IGM Port Mapping exists for Line ↔ Customs Port Code.
  3. Also check Package & Equipment mappings if flagged.
  4. Create the missing mapping, then Generate.

Documented An approved MCN is in play

IGM references Import Documentation, but when an approved MCN exists it pulls the latest commodity details from the MCN. The output may be correct even though it differs from the original.

  1. Check whether an approved MCN exists for the BL.
  2. Compare its latest commodity details against the IGM output.
  3. Only treat the IGM as wrong if it disagrees with the approved MCN.

Step 1 · Which action do you need?

New_knowledge_base

Three buttons, three different jobs. Not in the Dashboard at all? — that's upstream (Booking / BL / Voyage / mapping), not a Tracker action.

Documented Resend — send the same file again

Retransmits the existing outbound EDI via the configured FTP / SFTP / Email. Outbound only. You're not rebuilding anything.

  1. Open EDI → Transactions → EDI Tracker.
  2. Find the outbound record (filter by Ref ID / Partner / EDI ID).
  3. Select it and click Resend — it goes out via the configured method.

Documented Re-initiate — process it again

For the Failed Request queue. Fix the cause first; then LRP re-captures the data, builds a fresh request, and mints a new Request ID. Success → status Completed.

  1. Correct the underlying data / setup problem.
  2. Find the failed request in EDI Tracker; select it.
  3. Click Re-initiate → new Request ID → processes again → Completed.

contracts_knowledge_base Reset EDI — clear the log, start fresh

A Dashboard action, not a Tracker one. Clears the existing EDI log so the next generation is treated as New (new flag) rather than an amendment — under Message Function New or New and Update.

  1. In EDI Dashboard, choose the voyage and applicable Message Function.
  2. Reset the EDI log for that voyage.
  3. Generate again — created fresh, not as an amendment.

Field notes

New_knowledge_base

COPRAR / EDI5 (Load List) filters by BL status

Confirmed/Issued BL → included. Draft BL → excluded. No BL → excluded. Operations List View shows containers regardless of BL status, so Operations and Customs counts legitimately differ. "Visible in Operations, missing from COPRAR" → the BL is Draft or missing. Fix it in Documentation, not EDI.

Tracker is also an audit trail

Timestamp columns answer "was it really sent?" — SFTP Date, FTP Date, Email Date, Resend Date, Completed Date, Downloaded User/Date, Regenerated Date, and more.

Records can be hidden by role

EDI visibility is role-based — e.g. EMS EDI can be restricted to EMS users. "User A sees it, User B doesn't" is usually access rights, not a missing record.

Special inbound rules

New_knowledge_base

RCVS Booking Number fallback (all locations)

  1. Valid 15-digit Booking No in the EDI? → use it.
  2. Blank / invalid? → derive from the preceding SNTS move for that container.
  3. SNTS also invalid? → reject with Booking number is mandatory.

Rollback limits

Completed records can't be rolled back — they're already in Movement Entry and won't return to Error. Don't treat a Completed record like a failed one.

Cleared / deleted records have no rollback either. For Operation Reset cases, redo Load Confirmation in the Operations module.

"Mapping exists, but it still fails"

New_knowledge_base

"I checked, there is a mapping" is not the end of it. IGM mappings carry corporate / location context; COARRI mappings are Partner/EDI-specific and must match the actual BGM/segment. Walk the ladder:

  1. Correct mapping family (Port vs Package vs Equipment vs Movement)?
  2. Correct corporate / location context?
  3. Correct Partner?
  4. Correct EDI?
  5. Correct BGM?
  6. Correct segment?
  7. Only then move on to the next validation.
Location-sensitive. Don't ask only "does a mapping exist?" — ask "does it exist for the applicable context/location?" A mapping present for one corporate/location can be absent for another.

Four-layer troubleshooting model

New_knowledge_base

Every "EDI isn't working" ticket lands in one of four layers. Tap to see what belongs there — and a classic failure.

Documented Layer 1 · Business data

Is the underlying transaction right and at the required status? The Dashboard auto-fetches Vessel/Voyage/Bound/POL from Service, so wrong schedule data → wrong EDI. Classic: COPRAR missing TMP because reefer temperature isn't maintained — fix the data, not the mapping.

Documented Layer 2 · Interpretation / mapping

Can the values be represented for the partner? Missing Port Mapping → "Mapping yet to be created." Wrong segment for a partner's movement → EMS Gate error. See the Mapping tab.

Documented Layer 3 · Infrastructure / transport

Can the file actually travel? Tracker records Email / FTP / SFTP / HTTP dates. File correct but not received → Resend, don't rebuild the transaction.

Documented Layer 4 · Target validation

Received and interpreted, but the target module rejects it. EMS Gate applies business rules (BC, PA, IW, QM, duplicates). Fix the owning module; the back job auto-reprocesses.

Two "looks like setup, isn't" traps

New_knowledge_base

COPRAR missing the TMP (temperature) segment

TMP carries a reefer's set temperature. If temperature (even 0) is maintained, TMP shows; if not, the TMP and RNG segments simply don't appear. Don't change the mapping — maintain the temperature value and unit first. Pure Layer-1 business data.

EDI errored because the schedule wasn't ready

If schedule details are created after the file already errored, create/complete them, then reprocess in EDI Tracker — the file can move to Completed. The fix lives in Schedules, not EDI setup.

END Point Configuration — how EDI travels

your config

196 endpoints across 160 partners — the transport boundary (Layer 3). Four channel tabs: FTP/SFTP, Share Path, AS2, Web Service.

Protocol
SFTP on 190 · FTP on 6 — SFTP is the norm.
Transfer API
Enterprise DT on all 196 — the managed file-transfer engine.
Mode / Type
Active (192) · ASCII (195).
Per endpoint
URL, port, user, directory, RSA/DSA keys, encryption, schedule window & days, file count.
This is why a valid file can still fail. Generation and delivery are separate — a correct EDI can sit undelivered if the endpoint (host, key, schedule) is wrong. That's the Resend vs Re-initiate split.

EDI Rule Configuration — the rule layer

your config

11,145 rules across three tabs — EMS, BKG-BL, Documentations. Each maps a customer/party + port + movement to the external EDI Code a partner expects.

AP · SH (shipper) · BP · CN (consignee) · FP · NT (notify) — the party role.
Movement Code
LODE · RCVE · DCHE · DVAN · PVAN … the EMS movements.
EDI Code
109 · 119 · AE · CO · LD … the external value it maps to.
Scope
Per Partner + EDI + Customer + Port / Country.

The value/rule layer that sits alongside the code mappings — validations and code translation applied at generation.

The EDI vertical, by layer

Standards glossary

global
EDIFACTthe syntax
UN standard for EDI: messages built from segments and data elements, wrapped in interchange / group / message envelopes.
InterchangeUNB … UNZ
Outermost envelope — sender, receiver, date, control reference. UNZ echoes the reference back as an integrity check.
MessageUNH … UNT
One business document. UNH names it as type:version:release:agency (e.g. COARRI:D:95B:UN).
SegmentBGM, DTM, LOC…
A line of related data elements. Mandatory or Conditional; can repeat. BGM = beginning of message; LOC = location; EQD = equipment.
COPRARload/discharge order
Line/agent → terminal: order to load or discharge containers. In LRP: the EDI5 Load List.
COARRIload/discharge report
Terminal → line: confirmation that containers were loaded/discharged from the vessel. LRP turns it into EMS movements.
CODECOgate-in/out report
Terminal/depot → line: land-side gate moves (truck, rail, barge). Replaced the older COMORE message.
COPARNcontainer announcement
Container announcement / release exchanged between line and terminal.
BAPLIEbayplan
Stowage plan listing every occupied position on the vessel (bay-row-tier).
MOVINSstowage instruction
Line → terminal: how to stow containers on the vessel.
IFTMINshipping instruction
Consignment instruction to the carrier (ANSI X12 equivalent: 304).
IFTMBCbooking confirmation
Line → customer confirmation of a booking; may carry the VGM cut-off.
VERMASverified gross mass
The SOLAS VGM report — a container's verified weight, exchanged among shipper, weighing facility, terminal and line.
CUSCARcustoms cargo report
Carrier → customs cargo report / manifest. The global analogue of LRP's IGM.
CONTRLsyntax ACK
Acknowledges an interchange at the syntax level — received (technical) and accepted/rejected (functional). Not business content.
APERAKapplication ACK
Application error & acknowledgment — reports content/business errors, deeper than CONTRL.
ISO 6346container code
Standard for container identification and the 4-char size/type code (22G1 = 20ft standard, 45G1 = 40ft high-cube). Managed by BIC.
UN/LOCODEport code
UN code for ports, terminals and locations (INMAA = Chennai). Used on bills of lading and customs filings.
